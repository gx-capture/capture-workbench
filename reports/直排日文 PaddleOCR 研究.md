# 直排日文 PaddleOCR 研究

研究日期：2026-10-01。這一輪以現行程式、已安裝的 PaddleX 3.7 OCR 管線、PaddleOCR 官方文件，以及 `C:\software-dev\cert-prep\pdfs` 的四份 PDF 為準。`tmp/research-vertical-japanese` 只作參考，本輪沒有重跑那些實驗，也不把其中的 edit distance 當成結論。

## 結論

直排日文在這批試題上是同一頁裡的直欄，下面或旁邊仍是橫排選擇題。頁面本身是正放的。產品把每一頁用 PDFium 畫成圖，再交給 PaddleOCR 3.7.0 的通用 OCR 管線。辨識模型已經是含日文的 `PP-OCRv6_medium_rec`。

管線會把夠高的文字框轉成橫條再辨識，所以直排不是「模型完全不看直向像素」。框的順序則由 `SortQuadBoxes` 決定：由上到下，同一行再由左到右。日文直欄要由右到左。同一頁又有橫排題幹，不能把整頁或整份 PDF 轉 90 度，也不能把所有框都改成由右到左。

文字行方向模型只分 0 度與 180 度，而且產品 profile 強制關閉。它不負責把直欄認成直欄。

## 產品現在怎麼跑 OCR

`paddleocr==3.7.0`。Runtime 建立 `PaddleOCR(**kwargs)`，再 `pipeline.predict`。Profile 拒絕任何不是 `pp-ocrv6-medium-windowsml` 的設定，偵測與辨識必須是 `PP-OCRv6_medium_det` 與 `PP-OCRv6_medium_rec`，字典是 `rec/ppocrv6_dict.txt`。三個方向開關必須全是 false：`useDocOrientationClassify`、`useDocUnwarping`、`useTextlineOrientation`。呼叫端不能用 `targetLanguage` 換模型。

辨識結果在 `normalize_paddle_results` 依 Paddle 回傳順序接成頁面文字，中間用換行。空字串會先驗證多邊形再略過，不再讓整頁失敗。`CHANGELOG.md` 的 0.4.4 寫明：2024-07 這份 44 頁 PDF 的直排第 16 頁在 0.4.2 與 0.4.3 會整頁失敗，0.4.4 可以跑完；已知限制是直排日文辨得出來，但欄序不對，而且辨識錯誤比橫排多。本輪沒有重跑 OCR，所以沒有新的錯字數。

## 官方管線實際對直欄做了什麼

以下是已安裝的 PaddleX OCR 管線，不是舊筆記的轉述。

1. 偵測框先經過 `SortQuadBoxes`。程式註解寫的是由上到下、由左到右。實作先依第一點的 y、再依 x 排序；若相鄰框的 y 差小於 10，而且後者的 x 更小，就交換。橫排題幹因此會由左到右。頂端對齊的直欄也會由左到右。日文直欄要由右到左，這個排序沒有那個方向。
2. 每個框再由 `CropByPolys.get_rotate_crop_image` 做透視裁切。裁完若 `height / width >= 1.5`，做一次 `np.rot90`。這段不看 `use_textline_orientation`。對一條單純的直向像素，逆時針 90 度會把由上到下變成由左到右，方向與直欄閱讀一致。產品若再轉一次，會變成 180 度。
3. `use_textline_orientation` 為 false 時，每個裁切的角度記成 -1，不再轉。為 true 時才跑文字行分類。`rotate_image` 寫明類別只接受 0 或 1，角度是類別乘 180。官方模型表也寫 `PP-LCNet_x0_25_textline_ori` 與 `PP-LCNet_x1_0_textline_ori` 只有 0 度與 180 度。
4. 辨識批次會依裁切的寬高比重排以求速度，但結果寫回原本的框序。頁面文字順序仍是第 1 步的排序。

因此，夠高的直欄在進 `PP-OCRv6_medium_rec` 之前已經被轉成橫條。剩下的結構問題是這些橫條的左右順序，以及高寬比不到 1.5 的短直排、振假名沒有走進這次旋轉。

整頁方向模型 `PP-LCNet_x1_0_doc_ori` 分的是整頁 0、90、180、270 度。本輪畫出的直排頁都是正放的，直欄與橫排題在同一頁。把整頁轉 90 度會把選擇題一起轉歪。

## 官方模型對日文與豎排怎麼寫

PaddleOCR 3.7 的通用 OCR 產線可以選 PP-OCRv3 到 v6，預設是 `PP-OCRv6_medium`。v6 簡介寫 medium 與 small 的單一模型含簡體中文、繁體中文、英文、日文與 46 種拉丁語系；tiny 不含日文。同一頁的內部評測表把 `PP-OCRv6_medium` 的日文辨識寫成 90.5%，同表的 `PP-OCRv5_server` 是 73.7%。這是官方內部集，不是這四份 JLPT。

v6 那張辨識表沒有「豎排文本」一欄。v5 演算法頁有「竖直文本」：`PP-OCRv5_server_rec` 0.9314、`PP-OCRv5_mobile_rec` 0.8089，並寫模型支援手寫、豎版、拼音、生僻字。該欄沒有標成日文直排。產線頁另有一組日文分項，`PP-OCRv5_server_rec` 60.35%、mobile 54.65%，與上面的 73.7% 不是同一張表。

PaddleOCR 討論串 #14463 裡，協作者在 2025-09-27 寫：偵測把直排收成一條長框後，管線會把長框轉 90 度再辨識；並寫 PP-OCRv5 的直排主要覆蓋古籍，其他語言的直排相對弱。同一則把 `use_angle_cls=True` 說成直排旋轉開關。3.7 原始碼裡，90 度來自 `CropByPolys` 的高寬比，`use_textline_orientation` 只做 0 與 180。本輪以原始碼為準。

沒有官方的 `japan_PP-OCRv6`。多語表仍有 `japan` 這個舊語種縮寫，以及 `japan_PP-OCRv3_mobile_rec`。產品禁止用語言參數換模型。以 v6 自己的日文欄來看，沒有文件理由為了日文改回 v3 或 v5。這些替代模型也沒有在本輪跑過這四份 PDF。

PaddleOCR-VL 是另一條文件解析產線，不是現在這個 det／rec ONNX worker。本輪沒有拿它跑這些頁。

## 可以留在 PaddleOCR 裡的做法

依本輪看得到的版面與管線，優先序如下。

1. 只重排直欄，不動橫排題。在 `SortQuadBoxes` 之後，把高瘦、頂端對齊的一組框改成 x 由大到小。橫排題幹維持由上到下、由左到右。這對得上 2023、2024-07、2025 第 16 頁的「直欄在上、選項在下」，也避開 2024-12 第 16 頁這種全橫排頁。這是程式，不換模型。本輪沒有把它跑完一遍 OCR 來計錯字。
2. 維持官方那一次 `np.rot90`。高寬比已經達 1.5 的直欄不需要在產品裡再轉。短直排與振假名若低於 1.5，官方不會轉；要不要為這些小框補轉，是未測的程式調整。2023 第 16 頁的直欄旁看得到振假名。
3. 文字行方向模型只處理轉正之後上下顛倒。要開它必須改 profile，並交付 `PP-LCNet_x1_0_textline_ori`。它不是直欄閱讀順序的開關。
4. 整頁方向分類不對這批混排頁。頁是正的，直欄與橫排同時存在。
5. 換辨識模型要改 profile 身份與模型資產。官方表沒有顯示另一個 PaddleOCR 辨識頭在日文直排上高於 `PP-OCRv6_medium_rec`。v5 的「豎版」句子不能換成這份試題的準確率。
