# Capture Workbench v0.3 Pre-release Closeout Decisions

## Framing

Three reconciliation approaches were considered:

1. Add one authoritative closeout contract and retain older documents as
   historical evidence. This is accepted because it makes the expanded
   installer/native-import requirements explicit without rewriting completed
   historical work.
2. Edit every older specification in place. Rejected because it would erase
   why earlier release and desktop slices intentionally deferred these gates.
3. Delete conflicting records. Rejected because the existing evidence links and
   prior acceptance context remain useful.

The `v0.3.7` publisher recovery considered three narrower options:

1. Extend the `gh release download` stderr regular expression. Rejected because
   GitHub CLI 2.96.0 distinguishes an empty release (`no assets to download`)
   from a nonempty release whose assets miss the pattern
   (`no assets match the file pattern`), and human-facing text is not a stable
   inventory contract.
2. Use the already validated remote asset-name set to decide whether each
   candidate asset is absent or present. Accepted because absent assets can be
   uploaded directly while present assets still require downloaded byte
   comparison before any later mutation.
3. Upload every candidate asset unconditionally or with `--clobber`. Rejected
   because it would weaken the no-overwrite rule and could replace different
   draft bytes before validation.

## Accepted Decisions

- Change mode: edit + add. Prefer extending existing package, consumer, release,
  library, and desktop seams instead of parallel implementations.
- `v0.3.0` is consumed by a public GitHub Release and tag. The externally
  created annotated `v0.3.1` tag is also occupied and its workflow failed before
  producing a releasable candidate. The lightweight `v0.3.2` tag points to
  merge commit `8d5b3364320f60a1f16cf9ee222663150cb57c11`, but release run
  `30517094297` failed before any publication because Windows checkout changed
  the canonical source-lock bytes to CRLF. Preserve that tag and failure
  evidence; do not retag or manually publish around the workflow. The next
  synchronized candidate was `0.3.3`.
- The lightweight `v0.3.3` tag is immutable at
  `cfe570474a6925b4ad41a7c49685cae90f8aeebb`. Release run `30523583549`
  failed only after its redundant pre-staging `pnpm verify` encountered the
  intentionally unstaged Tauri sidecar and absent optional `pypdfium2`/Pillow
  worker dependencies. The publish job was skipped and no GitHub Release,
  assets, or package were created. Preserve the tag/run and move the candidate
  to `0.3.4`.
- The `v0.3.4` recovery is deletion-first: remove only the redundant release
  `pnpm verify`. Pull-request and `main` CI own full workspace
  lint/typecheck/test/build/package/desktop/smoke proof. Release must prove one
  successful exact-commit `main` push CI for the tag, then run only its retained
  release-specific reproducibility, integrity, candidate, and publication
  gates.
- The lightweight `v0.3.4` tag is immutable at
  `4d2e5cb5f3b5be1a0350ea4ca03c53e40cdd5c79`. Release run `30530781199`
  completed `build-candidate` successfully, then failed in publish preflight
  because the exact candidate size report had no installed-size evidence.
  Installed deterministic smoke had failed with unsafe cleanup, but the
  multi-command PowerShell block continued and masked that nonzero result.
  Publication preflight ran before any remote lookup or mutation; no GitHub
  Release, Release asset, or `0.3.4` package exists. Preserve the tag/run and
  move the candidate to `0.3.5`.
- The `v0.3.5` recovery makes native-command failure propagation explicit in
  block-style PowerShell steps, isolates installed-size smoke as a terminal
  step, and validates installed/startup evidence before budget comparisons.
  Expected nonzero commands remain narrowly custom-handled. Smoke diagnostics
  recursively render nested aggregate causes, but cleanup mechanics and
  publisher transaction order remain unchanged.
- The lightweight `v0.3.5` tag is immutable at
  `d3b466d640fc1c3a8424770b6a3c49cdd41cce05`. Release run `30568222541`
  completed `build-candidate`, including the production runtime, NSIS,
  size-only native install/uninstall proof, strict budgets, and candidate
  upload. Publish then failed in local preflight before any release/package
  mutation because `runtime-size-report.json` identified the raw build
  intermediate as `capture-runtime.exe`, while the candidate and runtime
  manifest used the canonical
  `capture-runtime-x86_64-pc-windows-msvc.exe` name. The exact runtime bytes
  and SHA-256 matched. No GitHub Release, Release asset, or `0.3.5` package was
  created; preserve the tag/run and move the candidate to `0.3.6`.
- The `v0.3.6` recovery keeps the report v2 and publisher checks strict. The
  bundle-size target measures the canonical executable already copied into
  `dist/release`, so `runtimeExecutable.path`, its basename `fileName`, bytes,
  and SHA-256 all describe the exact candidate/publication asset. Do not add a
  filename override, alias field, or relaxed preflight comparison.
- The lightweight `v0.3.6` tag is immutable at
  `fc9de8ed7feaf60f381bea97348de27f828646a6`. Release run `30576672375`
  completed `build-candidate`, including production runtime, NSIS,
  installed-size/native-uninstall proof, strict budgets, candidate assembly,
  and upload. Publish created draft Release `362689039`, then failed before its
  first asset upload because the publisher treated GitHub CLI 2.96.0's
  `no assets to download` result as unexpected instead of the known empty
  inventory. The draft remains unpublished with zero assets; no `0.3.6`
  package exists. Preserve the tag, run, and empty draft without cleanup or
  reuse, and move the candidate to `0.3.7`.
- The `v0.3.7` recovery keeps publisher transaction ordering and validation
  strict. `assertRemoteAssetNames` returns the validated remote inventory.
  `ensureDraftAssets` uploads a name absent from that inventory directly and
  downloads/byte-compares a present name. It performs a complete name-set and
  size/SHA-256 readback before package publication and again before making the
  draft public. No `--clobber`, alternate tag lookup, or human-facing
  GitHub CLI error-text dependency is introduced for known absence.
- Executable builds receive an explicit catalog path. Core builds use the
  checked-in unavailable-requirements catalog; production builds use the
  generated release catalog. A stale `dist/catalog` file can no longer
  implicitly override a core build and create an unstartable installer.
- PR #12 CI run `30542133653` failed in clean-runtime typecheck because ambient
  local packages had masked that the default locked development environment
  did not install Pillow or PDFium. Repair verification ownership in the `dev`
  dependency group while retaining both packages in `windowsml` and excluding
  them from core dependencies; do not weaken the existing type ignores or
  remove typecheck/tests.
- A core-only release-target split and CI latency optimization are separate
  follow-ups. Measured baselines are PR `22m20s` and `main` `20m40s`, dominated
  by installer/size verification (about 8-10 minutes), desktop verification
  (about 4m45s), and optional workers (about 2m40s). Later work may split and
  parallelize independent lanes, improve cache/artifact reuse, and tier
  PR/main/release without dropping any mandatory correctness gate.
- Preserve byte-exact canonical validation. Fix checkout behavior with one
  exact-path `.gitattributes` LF rule and prove it through a real temporary Git
  checkout configured with `core.autocrlf=true`; do not normalize CRLF while
  reading or broaden line-ending policy to unrelated JSON.
- Run the canonical source-lock classifier early in both CI and the release
  workflow so an incompatible checkout fails before expensive packaging or any
  publication step.
- The target organization now owns the live GitHub repository. Public metadata,
  schema IDs, release URLs, badges, and source links move to `gx-capture`.
  Historical links may remain only when explicitly labeled as historical.
- The public `v0.3.0` release contains no desktop installer. The Tauri identifier
  can therefore move to `io.github.gx-capture.capture-workbench` without
  displacing a public installed application.
- Angular Elements remains package-owned. Hosts never import it. The component
  UI uses Shadow DOM while the Angular/direct selector and custom-element tag
  remain distinct.
- A global `Symbol.for(...)` Observable registry is the single registration
  owner across bundle copies. Constructor branding distinguishes package
  idempotency from tag conflict.
- Packed consumer proof is upgraded from compile-only fixtures to real browser
  mounts rather than creating a separate unpublished browser bundle.
- The publisher is a resumable draft transaction. Public releases are
  immutable from this tool; unrestricted `--clobber` is limited to draft assets
  only after local preflight.
- Library recovery uses a small JSON journal and staged/backup files rather than
  adding a database. Policy and filesystem mechanism stay separately testable
  through failure injection.
- Direct deletion is rejected while a capture is active or a runtime ID is
  retained. A future cancel-and-delete UX may orchestrate cleanup, but ordinary
  delete cannot skip it.

## Phase 8 Transport Decision

Tauri 2.11 installed sources expose native drag/drop paths through
`getCurrentWebview().onDragDropEvent`. For interactive file selection, use the
official Tauri dialog plugin. Both routes converge on a Rust native-path import
command.

This is preferred over raw binary IPC because the required canonicalization,
symlink/special-file rejection, metadata-before-read limit, and path redaction
are naturally enforceable in one native owner. It is preferred over retaining
browser `File` reads because JSON number arrays multiply memory usage near the
50 MiB boundary.

The renderer may hold a selected path only long enough to call the private
command. It must not log, persist, export, or receive the path in a response.
The library copies verified bytes into its opaque document directory before any
runtime capture begins.

## Manual Boundaries

- GitHub Package visibility and write permission require authenticated
  organization confirmation.
- Branch protection and release-tag permissions require organization settings.
- No remote publication, release mutation, tag creation, branch-protection
  mutation, sibling-repository edit, commit, or push is part of the `v0.3.7`
  recovery implementation before independent review.
